# Test scenarios for the Current Workout module (2026)

Research note, written 2026-11-06. Scope: which test scenarios real-world sources recommend for `src/lib/workouts/index.ts`, a module with seven operations `(db, userId, ...)` (`start`, `get`, `addSet`, `removeSet`, `complete`, `history`, `deleteWorkouts`) over resources owned by a user and a small state machine: a Current Workout becomes a Completed Workout, and its Sets stop changing. Failures come back as values (`no-current-workout`, `set-not-found`). The refactor must not change behaviour. How to run these tests (Vitest, real Postgres, a fresh user per test) is settled in `testing-prisma-postgres.md` and ADR 0008, so this note doesn't repeat it. Bracketed numbers point to [Sources](#8-sources). Text marked **(analysis)** is my own reasoning, not a sourced claim.

## 1. TL;DR

- **Two users in every authorization test.** OWASP's IDOR cheat sheet gives the recipe: "Create User A and User B", have A use B's object references, and verify the denial "for all operations involving object references" [2]. The WSTG says the same [4], and API1:2023 adds "Do not deploy changes that make the tests fail" [1]. In this module that applies to `removeSet` and `deleteWorkouts` (they take IDs), and to the scoping of `get`, `history`, `addSet` and `complete`.
- **Assert the refusal and the absence of a side effect.** wger's ownership test checks both the 403 and that no row was written [7]. Saleor's "already completed" test checks the result and that the order count is unchanged [10]. Both read the database to do it. The house rule is stricter (no side-channel reads), so here "nothing changed" is observed through the module's own `get()` and `history()`, for the victim as well as the caller.
- **403 vs 404: no source requires 404.** RFC 9110 says a server that wants to hide a forbidden resource "MAY" answer 404 [5]. OWASP says that _if_ existence is sensitive, map both cases "to the same public response, such as a 404" [2]. wger does this by convention [6]. Returning `set-not-found` for someone else's Set is in line with all three, but it is a choice, not a requirement.
- **Invalid transitions:** acting with no Current Workout, completing twice (a double click), removing a Set from a Completed Workout, removing the same Set twice. Each test asserts the error _and_ that state is unchanged. Spree's double-submission bug is a documented case where the second request overwrote the first one's result [11].
- **Test through the interface.** SWE at Google, ch. 12: call "its public API rather than its implementation details", and "Test State, Not Interactions" [13]. Khorikov: the application database is a managed dependency, and "Communications with managed dependencies are implementation details" [14].
- **Prove each guard can fail.** This is a refactor, so the code already exists and red-first doesn't apply literally. Instead, break each guard by hand once and watch its test go red **(analysis)**. Beck lists the anti-patterns to avoid [16]. Stryker's Vitest runner can automate this, but it is optional [19][20].
- **The e2e suite covers only happy paths.** `e2e/workouts.spec.ts` and `e2e/sets.spec.ts` test create, read, complete and delete for one user. No test there covers a second user or an invalid transition. So the e2e suite is a characterization net for the happy path, and the new integration tests are the first coverage of the edges.

## 2. Object-level authorization (BOLA / IDOR)

- **What it is.** In BOLA the user is allowed to call the endpoint. The flaw is that they change an object ID and reach someone else's record [1]. API1:2023 recommends checking "in every function that uses an input from the client to access a record in the database" whether the logged-in user may act on it, and writing tests for that check [1].
- **How to test it.** OWASP's IDOR cheat sheet: "1. Create User A and User B. 2. Create objects owned by each user … 3. Authenticate as User A and attempt to access User B's objects by modifying object references in requests. 4. Verify that the application denies unauthorized access regardless of whether the object identifier is predictable or unguessable" [2]. The WSTG: "The best way to test for direct object references would be by having at least two (often more) users to cover different owned objects and functions" [4]. Set IDs are UUIDs, and the cheat sheet says access control "is crucial even with these identifiers" [2].
- **How to implement it.** "Prefer a lookup limited to documents owned by the current user" [2]. The old `deleteSetServerFn` already did this. The module's `removeSet` keeps the same filter (`where: { id, workout: currentWorkoutWhere(userId) }`) and turns the find-then-delete into a single `deleteMany`.
- **Not leaking existence.** RFC 9110 §15.5.4: "An origin server that wishes to 'hide' the current existence of a forbidden target resource MAY instead respond with a status code of 404 (Not Found)". §15.5.5 defines 404 as the server not finding a representation "or is not willing to disclose that one exists" [5]. OWASP: "If the resource's existence is sensitive, use the scoped lookup and map both cases to the same public response, such as a 404 (Not Found) response" [2]. The Authorization Cheat Sheet adds only general rules, "deny access by default" and validate "on every request", with no status-code advice [3]. **(analysis)** For the module, "the same public response" means a test that compares `removeSet(A, B's setId)` with `removeSet(A, randomUUID())` and expects identical results.
- **Mutation by a foreign reference vs lookup of a foreign object.** wger's suites keep the two apart. When a _referenced_ foreign key belongs to someone else on create (`slot_entry`, `day`), the test expects 403 and also asserts that no log was written [7][8]. That is the class of bug in wger advisory GHSA-rjpf-7pf5-q54x, where a missing ownership check on `slot_entry` let one user write logs into another user's progression data [9]. When the _looked-up_ object is filtered by owner, the base test expects 404, with the comment "they don't leak that the object exists" [6]. In Setlist, `removeSet` is the second case. `addSet` with another user's `movementId` is the first case and belongs to movement ownership (ADR 0001), so it is out of scope (section 7).

## 3. Invalid transitions and double submits

- **The real-world failure.** Spree PR #4499 (2014): "two requests complete an order in rapid succession … This results in a success followed by a failure (double submission) which overwrites the payment state to failed". The "processing" state meant to block it was never persisted, "because it is set within a transaction" [11]. A follow-up PR from the same author removed the transaction around payment transitions for a related rollback problem [12]. Both were closed unmerged. **(analysis)** The lesson for this module: a second `complete` must not alter the workout the first one completed. `complete` looks up by `completedAt: null`, so a second call finds nothing and returns `no-current-workout`. A test should pin that down, and also check that the Completed Workout in `history()` still has its Sets and was not duplicated.
- **What an idempotent "complete" looks like elsewhere.** Saleor's `test_checkout_complete_order_already_exists` calls complete on a checkout that has already become an order. It expects no errors, the existing order returned, and `Order.objects.count() == orders_count` [10]. Setlist returns an error value instead of the existing workout. Both designs are defensible. The test only has to lock in the current one (it's a pure refactor), and the rule it must enforce is the same: nothing new is created.
- **Assert that state is unchanged, not only the error.** SWE at Google gives the reason for state checks: an interaction-only test "will pass even though we would have wanted it to fail" if the record is later deleted [13]. **(analysis)** Each failure test therefore ends with a `get()` or `history()` call for every user it touched.

## 4. Observing outcomes through the interface

- SWE at Google, ch. 12: write tests that "invoke the system being tested in the same way its users would; that is, make calls against its public API rather than its implementation details". Its brittle example reads and writes the database directly ("Write the balance to the database directly") and "peers into the system's internal state" [13].
- Khorikov (2020): the application database is a managed dependency, "only accessible through your application"; "Communications with managed dependencies are implementation details", and "You don't want your tests to turn red every time you split a table in the database" [14]. The post doesn't explicitly forbid reading database state in assertions. The no-side-channel rule is this repo's stricter reading of the same idea **(analysis)**.
- Kent C. Dodds: "The more your tests resemble the way your software is used, the more confidence they can give you", and tests coupled to implementation details produce false negatives when you refactor [15]. The case against mocks is already in `testing-prisma-postgres.md` §2.

## 5. Proving the tests can fail

- Fowler's TDD summary: write a test for the next bit of functionality, "Write the functional code until the test passes", then refactor [18]. Beck's Canon TDD starts from "a failing test" and lists the mistakes that hollow a test out: "delete assertions so the test pretends to pass", and "copying actual, computed values & pasting them into the expected values of the test. That defeats double checking" [16].
- For code that already exists, Feathers' characterization test is the honest version: supply "a dummy expectation value, and then running the test to find the actual value". Its purpose is "to document your system's actual behavior, not check for the behavior you wish your system had" [17]. That fits a pure refactor: write the tests against the old server functions' behaviour, then move the code.
- **Manual mutation (analysis).** For each guard, break it once, run the suite, and confirm a test goes red. Guards to break: drop `userId` from the `removeSet` filter, drop `completedAt: null` from it, drop `userId` from `deleteWorkouts`, make `complete` ignore `completedAt`. A guard whose removal leaves everything green has no real test.
- **Stryker (optional).** Stryker inserts mutants and counts a mutant as killed when "at least one of your tests fail" [19]. `@stryker-mutator/vitest-runner` 10.1.1 (2026-10-23) needs `vitest >=2` [20]. Its `related` option (default true) is fine here because the tests import the module directly. Its `vitest.pool` defaults to `threads`, so set it to `forks` to match ADR 0008 [20]. Each mutant reruns the suite against Postgres, so a full run will be slow **(analysis)**. Make the manual check the default.

## 6. Scenario table

"A" is the user under test, "B" a second user. "Observe" means the follow-up call that shows state is unchanged. Every row is the behaviour of the server functions before the refactor, which the module keeps. Every row has a test in `src/lib/workouts/workouts.test.ts`. Row 15 is tested in a stricter form: both users have a Current Workout, and only the caller's changes.

| #   | Scenario                                        | Operations                               | Expected result                                                  | Observe                                           |
| --- | ----------------------------------------------- | ---------------------------------------- | ---------------------------------------------------------------- | ------------------------------------------------- |
| 1   | Start, add Sets, read back                      | `start`, `addSet`, `get`                 | `get` returns the Current Workout with each Set and its Movement | —                                                 |
| 2   | Complete moves the workout to history           | `complete`, `get`, `history`             | `ok`; `get` is null                                              | `history` has one entry with its Sets             |
| 3   | History is newest first                         | `complete` ×2 (start between), `history` | ordered by `completedAt` desc                                    | —                                                 |
| 4   | Add a Set with no Current Workout               | `addSet`                                 | `no-current-workout`                                             | `get` still null (no workout created on the side) |
| 5   | Complete with no Current Workout                | `complete`                               | `no-current-workout`                                             | `history` unchanged                               |
| 6   | Complete twice (double click)                   | `complete` ×2                            | `ok`, then `no-current-workout`                                  | `history` has exactly one entry, Sets intact      |
| 7   | Add a Set after completing                      | `complete`, `addSet`                     | `no-current-workout`                                             | the Completed Workout's Sets are unchanged        |
| 8   | Remove a Set of a Completed Workout             | `removeSet`                              | `set-not-found`                                                  | `history` still shows the Set                     |
| 9   | Remove the same Set twice                       | `removeSet` ×2                           | `ok`, then `set-not-found`                                       | `get` lacks that Set, other Sets intact           |
| 10  | A removes B's Set                               | `removeSet(A, B's set)`                  | `set-not-found`                                                  | B's `get` still lists the Set                     |
| 11  | B's Set id and a random UUID look the same to A | `removeSet`                              | identical results                                                | —                                                 |
| 12  | A deletes B's Completed Workout                 | `deleteWorkouts(A, [B's id])`            | `ok` (silently ignored)                                          | B's `history` unchanged                           |
| 13  | Mixed own and foreign IDs                       | `deleteWorkouts(A, [A's, B's])`          | `ok`                                                             | A's entry gone, B's `history` unchanged           |
| 14  | A's reads never show B's workouts               | `get`, `history`                         | A sees null / empty while B has both                             | B's `get`/`history` unaffected                    |
| 15  | A acts while only B has a Current Workout       | `addSet`, `complete`                     | `no-current-workout`                                             | B's `get` unchanged, no new Set                   |
| 16  | Start after completing                          | `complete`, `start`, `get`               | new empty Current Workout                                        | the old one still in `history`                    |

**Current behaviour the refactor keeps (analysis):**

- `deleteWorkouts` filters by `userId` only, not by `completedAt`, so a Current Workout id sent straight to the server function deletes it. The screen never sends one. The refactor keeps this but **doesn't pin it with a test**, because the planned empty-workout flow (`docs/research/empty-workouts.md`) restricts `deleteWorkouts` to Completed Workouts. It deletes the Sets and then the workouts in two statements, and always returns success.
- `addSet` twice with the same input creates two Sets. Two identical Sets are a valid log, so nothing deduplicates a double click on "Add set".
- `get` orders by `id desc`, and the IDs are UUIDs. With more than one open workout the pick is arbitrary (ADR 0006's context). Before the refactor, `addSet` and `complete` didn't order at all, so they could act on a different open workout than the one `get` showed. The module now picks the same one for all three. Tests that call `start` once per user never hit this.
- `completedAt` is `new Date()`, stored to the millisecond. If two `complete` calls in row 3 land in the same millisecond, the order is a tie. The history test waits 5 ms between them.

## 7. Not covered here, and why

- **`start` while a Current Workout exists, and two concurrent `start` calls.** Today `start` is a plain `create`, so it makes a second open workout. The partial unique index and `ON CONFLICT` start described in ADR 0006 belong to that later issue, and so does the race test. Until then, no test should call `start` twice for one user.
- **`addSet` with another user's Movement.** That is movement ownership (ADR 0001), the "foreign reference" case from section 2.
- **The order of Sets inside a workout.** Sets have no timestamp, so there's nothing stable to order by yet.
- **Body-weight Sets and Load** (ADR 0003): not part of this refactor.
- **Input validation** (`reps >= 1`, `weight >= 0`): this stays in the zod schema in `src/lib/workouts/set-draft.ts`, which the server functions run before calling the module.
