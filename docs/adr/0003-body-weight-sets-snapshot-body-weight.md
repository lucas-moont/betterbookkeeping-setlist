# Body-weight sets snapshot body weight and record added weight apart

For a Set of a Body-weight Movement, `weight` holds the Body Weight Snapshot: the user's latest body weight, copied in when the set is logged. Extra load or assistance goes in a signed, nullable `addedWeight`, with `addedWeightNote` required whenever `addedWeight` is set (for example `+10`, "weighted vest", or `-20`, "red band"). For any other movement `addedWeight` is null and `weight` is what's on the bar. Load is always `weight + coalesce(addedWeight, 0)`, so every Metric uses one formula for every set.

We snapshot instead of joining Sets to Body Weight Entries at read time. That way recording, editing, or deleting a body weight never rewrites past Progression Charts.

## Considered Options

- **Store the total Load in `weight`, with the snapshot and added weight beside it.** Queries get slightly simpler, but the same fact is stored twice and the copies can drift.
- **Store no weight on body-weight sets, and look up the body weight for that date when reading.** No duplication, but history changes whenever the user corrects an old entry, and every metric query needs a date-range join.

## Consequences

The snapshot is locked: the form never lets the user change the base weight of a body-weight set, so there is exactly one way to express "I lifted more than my body", which is Added Weight with a note. The server enforces it too: it ignores the weight the form sends and copies the Latest Body Weight. The one exception is a user with no Body Weight Entry yet. The form asks for their body weight (above 0, or `body-weight-required`), uses it as the snapshot, and records it as today's Body Weight Entry, in the user's time zone, in the same transaction as the Sets.

The snapshot is taken each time a Set becomes completed: when it is added, and again when it is completed after being un-completed (ADR 0011). With no Body Weight Entry left by then, the Set keeps the weight it had. Completing a Set that is already completed takes no new snapshot.

Two guards keep the snapshot honest. Added Weight can be negative, but never below `-weight`, so Load is never negative. Three CHECK constraints in the `set_body_weight_and_added_weight` migration back the module's own refusals: Added Weight and its note come together or not at all, Added Weight is never below `-weight`, and only a body-weight Set carries Added Weight (`added-weight-not-allowed` otherwise). The bound is checked again on every new snapshot: a lower Latest Body Weight can put an old assistance above it, so completing that Set again returns `assistance-exceeds-body-weight` and leaves it planned. The module checks against the exact weight it writes, so the user gets that code and never a CHECK violation. And a Body Weight Entry can't be dated in the future, or it would become the Latest Body Weight and be copied into every new set until that date arrives. The form and the server both reject dates after the user's today, read in the time zone from the `tz` cookie (ADR 0004). An earlier draft had the server allow UTC today plus one day, back when it didn't know the zone. The cookie is set by the browser, so a user could send another zone, but the furthest-ahead zone is UTC+14, so the server never accepts a date past UTC today plus one day either way, and only the user's own entries are at stake. For an honest browser the rule is exact. Without the cookie (the first render of a first visit) both sides fall back to UTC, so they still agree.

The body-weight flag can be turned on or off after sets exist, and existing sets are left alone. Each Set copies the flag into its own `Set.isBodyWeight` when it is added, and that column never changes. It, not the Movement's current flag, decides whether a Set takes a new snapshot when completed again: a Set logged with a barbell keeps its bar weight after the flag is turned on, and a Set logged as body-weight still takes the Latest Body Weight after it is turned off. Load never reads either flag, so every set stays correct. The Movement's flag only changes the default and the form for sets logged afterwards, so no data migration is needed. Sets logged before `Set.isBodyWeight` existed got `false`, even on Movements already flagged: their weight is whatever the lifter typed, not a snapshot.
