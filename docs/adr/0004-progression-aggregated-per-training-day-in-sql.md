# Progression is aggregated per Training Day in SQL, in the browser's time zone

A Training Day is the calendar date on which a Workout was completed, in the user's time zone. The server doesn't know that zone, so the browser stores its IANA zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`) in a `tz` cookie, and the server reads it, during SSR as well as in server functions. The server validates it with `new Intl.DateTimeFormat("en", { timeZone })` inside a `try`, and Postgres groups the sets by `("completedAt" AT TIME ZONE 'UTC' AT TIME ZONE $tz)::date`, returning one row per day with Max Weight, Total Reps, and Total Volume. Prisma's query builder can't group by a computed date, so this query uses raw, parameterised SQL (`$queryRaw`). The only other raw SQL is the `INSERT ... ON CONFLICT` that starts a workout (ADR 0006).

## Considered Options

- **Compute in the browser from the workout history query.** No new query, but it downloads every set the user has ever logged, and that grows without limit.
- **Store a time zone on the user.** Needs a settings field, and the dates come out wrong while the user travels.
- **Send the zone with each query and skip SSR for zone-dependent data.** No cookie, but server-rendered dates (the workout history, the default "today" in forms) would still come out in the container's UTC, and progression would be the one query that breaks the `ensureQueryData` + `useSuspenseQuery` pattern.
- **Validate against `Intl.supportedValuesOf("timeZone")`.** That list has no `"UTC"` (what headless Chromium sends on a UTC CI runner) and only old spellings such as `"Asia/Calcutta"`, so valid browsers would be rejected.

## Consequences

The browser owns the calendar everywhere, not just here. A Body Weight Entry's date is stored as a Postgres `date`, but Prisma returns it as a JS `Date` at UTC midnight, and a browser west of UTC (São Paulo) would show it as the day before. Calendar dates therefore cross the server-function boundary as `"YYYY-MM-DD"` strings, and the browser sends "today" as a string too.

On the very first visit there is no `tz` cookie yet, so that one server render uses UTC; the browser then sets the cookie and invalidates the router, so the same page re-renders in the user's zone, and every later render uses it from the start. That invalidate can land while a lazily loaded route is still hydrating, and the router's store hands every reader its current state, so `useTimeZone()` hydrates with the zone the server rendered in, read from the cookie when the module loads, and only moves to the context's zone once hydrated (`useHydrated` from the router, a `useSyncExternalStore` whose server snapshot is `false`). The time zone is the only value of the root context that changes on that first-visit invalidate; any other that starts changing there needs the same treatment. The client reads the same cookie, not `resolvedOptions()`, so server and client render the same dates and build the same query key. If Postgres doesn't know a zone name that ICU accepts, the query returns an `invalid-time-zone` error code instead of a 500. Prisma 7 with adapter-pg wraps that Postgres error (SQLSTATE `22023`) in a `P2010`, and only that combination maps to the code; every other error still throws. The query computes the day once, in a subquery, and groups by it: Prisma numbers each `${tz}` as its own parameter, so writing the expression again in `GROUP BY` fails with `42803` (docs/research/body-weight-sets-and-progression.md §7). The movement picker's count of Training Days uses the same expression, so it counts days in the user's zone too, and its query key carries the zone like the chart's.

The same data can produce slightly different charts when viewed from two time zones. That's acceptable: the chart answers "what did I lift on the days I remember", and those days are in the user's local time.
